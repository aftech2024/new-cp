## Deploy (Hostinger)

Live at https://aftech.co.id. Two routes to production, both landing in
`/home/u532067520/domains/aftech.co.id/public_html`.

**Automatic** — every push to `main` runs `.github/workflows/deploy.yml`: build,
sanity-check `dist/`, rsync over SSH, then smoke-test the live URLs. Credentials
come from repo secrets (`HOSTINGER_HOST`, `_PORT`, `_USER`, `_REMOTE_DIR`,
`_SSH_KEY`); the `VITE_*` build values come from repo variables.

**Manual** — from a machine with `deploy.config` filled in (see
`deploy.config.example`):

```bash
npm run deploy:dry    # preview the file list, upload nothing
npm run deploy        # build, verify, upload
```

Afterwards, purge the CDN cache in hPanel (Dashboard → Cache → Hapus cache);
that step is not automated.

### The web root is shared

`public_html` also hosts `adminklinik`, `budget`, `eptms`, `erp`, `klinik`, `mk`
and `smart`. Two consequences:

- Deploys never delete. `DELETE_STALE=0` in `deploy.config`, and the workflow
  runs rsync without `--delete`, so a stray local deletion can never take a
  sibling app down. Stale hashed assets are pruned deliberately with
  `npm run clean:assets` (scoped to `assets/`, nothing else).
- `public/.htaccess` excludes those paths from the SPA rewrite, so their URLs
  reach their own front controllers instead of `index.html`.

Both the workflow's smoke test and any manual check should confirm those sibling
paths still return 200.

### After a content or config change

`$RECIPIENT_EMAIL` in `public/api/contact.php` is the contact-form inbox.
`VITE_SITE_URL` in `.env` drives canonical and OG URLs — the build fails the
sanity check if `example.com` placeholders survive into `dist/`.

The PHP endpoint cannot be exercised locally (no PHP runtime in the dev
environment), so submit a real test message after deploying and check the
recipient's spam folder — `mail()` from shared hosting is frequently filtered.

## Chat assistant

The floating chat button (`src/components/chat/ChatWidget.tsx`) talks to
`public/api/chat.php`, which proxies to the Anthropic API and answers only about
Aftech. Its knowledge is `dist/api/chat-knowledge.txt`, generated by
`scripts/prerender.ts` from `src/data/` on every build — edit the data, rebuild,
and the assistant follows.

Knowledge that belongs in chat but not on the pages — the everyday words
visitors use for each service ("bikin web", "pasang CCTV") and the FAQ that
comes up in conversation — lives in `src/data/assistant-knowledge.md`, plain
Markdown appended to the generated file as-is. Add an entry there whenever the
assistant misses something, then push; the deploy rebuilds the knowledge.

To find what is missing, the assistant flags every question about Aftech its
knowledge could not answer, and `chat.php` appends it (question and answer, no
IP) to `/home/u532067520/domains/aftech.co.id/aftech-chat-gaps.jsonl`.

The API key is never in the repo or the bundle. On the server it lives one level
above the web root, at
`/home/u532067520/domains/aftech.co.id/aftech-chat-secret.php`:

```php
<?php return 'sk-ant-...';
```

If Anthropic fails (network error, rate limit, overload, out of credit) the same
conversation goes to the OpenAI-compatible fallback set by `$FALLBACK_BASE_URL` /
`$FALLBACK_MODEL` in `chat.php` (9router). Its key lives beside the first, at
`/home/u532067520/domains/aftech.co.id/aftech-chat-fallback-secret.php`, in the
same `<?php return '...';` form. Failures are logged to the PHP error log as
`aftech chat anthropic error` / `aftech chat fallback error`.

Without either key file the endpoint returns 503 and the widget tells visitors to
use WhatsApp or the contact form. Limits (message length, turns per conversation,
per-IP and global daily caps, `max_tokens`) are in the config block at the top of
`chat.php`.

Visitors can attach a photo (downscaled to 1280px in the browser, one per
message, 10 per IP per day), dictate with the microphone and have answers read
aloud (both via the browser's Web Speech API), copy answers, and browse past
conversations (stored in their own browser only). Thumbs up / down ratings go
to `public/api/chat-feedback.php`, which appends one JSON line per rating —
question, answer, rating, no IP — to
`/home/u532067520/domains/aftech.co.id/aftech-chat-feedback.jsonl`. Read it in
hPanel's File Manager to see which answers need better source data.

Local test with Herd's PHP (its `auto_prepend_file` must be disabled):

```bash
npm run build
ANTHROPIC_API_KEY=sk-ant-... php -d auto_prepend_file= -S 127.0.0.1:8080 -t dist
```

Add `FALLBACK_API_KEY=sk-...` to exercise the fallback; set only that one to
test it on its own.
